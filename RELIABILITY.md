# AgentDesk release and reliability roadmap

23 November 2026 · Windows x64 · AgentDesk 0.3.0

AgentDesk is a personal Windows assistant for local files, software tasks, research, browser work and repeatable workflows. Release 0.3.0 addresses problems found in the initial code audit. Production readiness depends on evidence from the installed application and from each enabled integration.

| Area | Release 0.3.0 | Next engineering milestone |
| --- | --- | --- |
| Desktop runtime | Electron 45.4.1 in the Windows package, one application instance, isolated renderer and restricted navigation. | Sign the installer with a verified publisher and test in-place upgrades on supported Windows versions. |
| Local backend | Per-launch credentials for HTTP and WebSocket calls. The renderer can reach the service on loopback. | Add startup diagnostics for runtime, model, browser, terminal and storage. Test recovery after the Python process exits unexpectedly. |
| Models | Provider-specific endpoints, models and credentials. External fallbacks are opt-in. Hard mode tries OpenRouter and then local. | Maintain capability and cost metadata per route. Compare each route on the same real tasks and record completion, cost and latency. |
| Tool execution | Validate tool arguments and apply action policies. A provider failure after tool execution cannot trigger a second provider to replay the run. | Classify tool effects centrally, log redacted results and require scoped approvals for sensitive actions. Use a separate worker and actual OS isolation for untrusted code. |
| History and memory | Compaction preserves originals in transcript archives. Workflow recording is optional. | Let users review and remove retained facts and learned workflows. Scope retrieval to an explicit workspace and keep source provenance. |
| Background tasks | Run outcomes distinguish failures, cancellation and step limits. | Persist jobs, steps, attempts and approval state in SQLite. Make interrupted runs resumable with explicit handling for actions whose outcome is unknown. |
| Browser and extensions | Chromium sandboxing is enabled. Fresh installations require users to enable MCP servers explicitly. | Give each workflow a separate profile, verify external destinations before transfers and record which connector acted. Pin extension versions and scope credentials per server. |
| Credentials | Windows protects saved model and service keys with DPAPI. Backup creation excludes settings, MCP configuration and the workspace key. | Move connector secrets into a dedicated credential store and build a migration check for encrypted profiles. |

## Design choices behind the next release

1. **Keep workflow control in the application.** Let the model propose the next action and let the runtime enforce its permissions, deadline and input schema. Use explicit states for running, awaiting approval, cancelled and failed. Record a durable step key before executing an external action. If the process stops after dispatch, reconcile the action's result before retrying. LangGraph documents thread state and persisted checkpoints as a reference design. AgentDesk can implement the same essential semantics in its existing SQLite backend and assess whether a workflow framework would reduce maintenance once workflows grow. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
2. **Evaluate completed work and permitted side effects.** Build a fixture set around actual workflows. Check the files and their contents, the records the assistant changed, whether it requested permission, and whether it called a tool twice. Compare the local model and at least one configured cloud model against the same fixtures. Use redacted local traces with run ID, provider, tool name, elapsed time, result status and policy decision. Prompt text, provider keys, file contents and screenshots should be excluded from default traces. [OpenAI agent evaluation](https://developers.openai.com/api/docs/guides/agent-evals) · [Agent improvement with traces and evals](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)
3. **Treat browsers and external tool servers as separate trust boundaries.** Extract needed web data into structured fields. Put purchase, account, email and other consequential actions behind review. Prefer an authorized API or a named, allowlisted workflow over open-ended browser actions for recurring tasks. MCP servers run with OS permissions, so restrict their environment and filesystem access. Use expiring execution sessions with resource and network limits for external code. [OpenAI agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety) · [MCP security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
4. **Track the Windows runtime independently of model features.** Keep Electron on a supported major version, confirm its bundled Chromium version, and rerun install and upgrade checks for each update. Assess installed Python and Playwright dependencies against a lockfile and generate a software bill of materials. Plan rollback alongside installer signing. [Electron release policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) · [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security/) · [Electron 45.4.1 release](https://releases.electronjs.org/release/v45.4.1)
5. **Measure browser tasks in a disposable environment.** Keep a small local suite with forms, downloads and failed navigations. Evaluate outcomes from saved evidence and compare it with a public benchmark such as BrowserGym. Where Windows Sandbox is available, use a read-only input folder and disable networking for clean installer and offline model tests. NIST's AI Agent Standards Initiative treats agent interoperability, reliability and secure authorization as active areas of standards work. [BrowserGym](https://github.com/ServiceNow/BrowserGym) · [Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file) · [NIST initiative](https://www.nist.gov/super-intelligence/si-agent-standards-initiative)

## Release acceptance checks

| Scenario | Evidence required |
| --- | --- |
| Installer and upgrade | Install on a clean Windows test account. Launch from Start and the desktop shortcut. Upgrade from 0.1.0 and verify the original sessions and workspace survive. |
| Offline chat | With cloud fallback disabled, start the local model, stream a response and run a local file task. Record startup latency, memory and tokens per second on the target PC. |
| Cloud chat | Run the same fixture with each configured provider. Check a rate limit, an invalid key, a streamed interruption and a model with unsupported tools. |
| Access control | Requests from an unrelated webpage, unauthenticated local clients and invalid WebSocket clients are rejected. A denied action leaves the filesystem and external service unchanged. |
| Browser and screen | Navigate to a harmless page, read it, take a desktop screenshot with approval and test a cancelled action. Check login and logout with disposable accounts. |
| Files and terminal | Upload a CSV, create an output in the selected workspace, open the preview and run an approved benign command. Reject traversal outside the workspace. |
| Missions and recovery | Pin a task and rerun it from a different session. Interrupt an automation and verify the saved outcome and next run. Verify that resuming a task cannot duplicate an external action. |
| Research workflows | Produce an editable lecture-outline artifact and audit a small GIS CSV. Verify sources, row counts, units and output filenames against fixtures. |

Use the included regression script for the local API and mock model checks. Live browser sign-in, cloud models, optional Windows tools and install or upgrade tests require a regular Windows test session and the relevant accounts.
