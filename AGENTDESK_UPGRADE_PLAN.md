# AgentDesk upgrade plan

23 November 2026 · Windows x64 · CPU-first · Baseline AgentDesk 0.3.1

## Recommended direction

Ship **0.3.2 as a release-reliability update**. Follow with **0.4.0 for safe, resumable workflows**. After that, tune the local model and ship the workflows that pass tests on this PC. Keep Electron, React, FastAPI, SQLite and llama.cpp. Use local processes and databases on Windows, with Docker-free setup and offline chat.

### Execution isolation decision

Start with restricted operations and explicit approval for high-impact actions. Use Windows Job Objects for process lifetime and resource ceilings, and verify that cancellation cleans up descendants. Treat Win32 AppContainer or another proven OS isolation boundary as a separate prototype for running untrusted code. Test filesystem reach, network access and credential exposure using harmless fixtures before enabling arbitrary execution. A separate process, an Electron renderer sandbox and a Job Object solve different problems. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) · [Electron sandbox model](https://www.electronjs.org/docs/latest/tutorial/sandbox/)

### CPU evaluation and workflow pilots

Start with a versioned set of 30 fixtures. Run each candidate three times on the same machine and compare against 0.3.1. Score output artifacts and policy decisions independently. Use an initial engineering target of at least 90% success on deterministic starter workflows and 100% on critical approval, offline, and no-duplicate-action tests. Treat model latency and memory figures as baseline measurements before setting a promotion threshold.

## Research decisions

- **Windows packaging.** Electron maintains the latest three stable major lines under its support policy. Align development and release versions and confirm the exact supported patch for the release date. Prefer NSIS if the full offline bundle passes. Check the custom footer against the PE certificate-table layout before signing a wrapper, then verify signature and timestamp on the final bytes. Windows Sandbox has edition requirements, so the default local plan uses a disposable Windows profile. [Electron support policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) · [NSIS](https://www.electron.build/docs/nsis/) · [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) · [SignTool verification](https://learn.microsoft.com/en-us/windows/win32/seccrypto/using-signtool-to-verify-a-file-signature) · [Windows Sandbox editions](https://learn.microsoft.com/en-in/windows/security/application-security/application-isolation/windows-sandbox)
- **Storage and memory.** Use transactions and a unique run key for work claims. A short transaction that marks an action dispatched and an external action itself are separate operations. Implement recovery accordingly. Use SQLite FTS5 later for opt-in local search with workspace scoping and deletion if task tests show value. [SQLite WAL](https://www.sqlite.org/wal.html) · [SQLite FTS5](https://www.sqlite.org/fts5.html)
- **Tool and browser boundaries.** Apply least privilege and verify effects at the execution boundary. Use role or label-based locators that wait for actionable elements. Use isolated browser contexts and an explicit profile opt-in for real accounts. Preserve client-side permission denial and backend validation as independent checks. [OWASP excessive agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) · [MCP security](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices) · [Playwright actionability](https://playwright.dev/docs/actionability) · [Playwright isolation](https://playwright.dev/docs/browser-contexts)
- **Cloud routing.** Start with the existing OpenRouter free route. Its account and provider limits vary, so surface rate-limit and route status, honor retry headers, and verify remaining quota in a disposable live test. Use local-only defaults for private workspaces and validate data policies before sending eligible context. Add another provider after a measured availability gap and a current API, pricing and terms review. [OpenRouter free models](https://openrouter.ai/collections/free-models) · [OpenRouter free router](https://openrouter.ai/openrouter/free) · [OpenRouter privacy](https://openrouter.ai/privacy/)

Defer a public A2A endpoint, a second inference runtime, vector storage, general-purpose autonomous workers and automatic updates until install and workflow recovery gates pass. Those are separate product decisions. All release tests above can be designed without Docker.

## First implementation sequence

1. Write the deterministic package and smoke-test matrix around the existing 0.3.1 artifact.
2. Run the install and upgrade tests on disposable data with explicit approval for a real installer confirmation.
3. Ship the 0.3.2 installer and release evidence once its gates pass.
4. Start the scheduler migration and the shared execution policy together in 0.4.0.

This audit inspected source and verified the prior package bytes. It did not execute the installer, change application code or exercise cloud credentials. The existing 0.3.1 build remains the comparison baseline.
